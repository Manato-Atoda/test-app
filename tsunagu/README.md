# つなぐ — 社内SNS（試作）

企業ごとに閉じた社内SNSです。アカウントは企業の管理者だけが発行でき、社員は
**企業コード ＋ 社員コード（またはメールアドレス）＋ パスワード（またはパスキー）** でログインします。

| 部分 | 中身 | 対応 |
| --- | --- | --- |
| [`server/`](server/) | API サーバー・管理コンソール（Web）・パスキー用ページ。Python 3.9 以上の標準ライブラリだけで動く | どこでも |
| [`app/`](app/) | 社員向けアプリ（Flutter） | iOS / Android / macOS / Windows |
| [`docs/API.md`](docs/API.md) | API 仕様 | — |

## すぐ試す（開発用）

```bash
python3 tsunagu/server/run.py serve --seed-demo
```

- 管理コンソール: http://localhost:8790/admin
- デモ企業: 企業コード `DEMO`。社員 `E0001`（管理者）〜 `E0004` は発行済み、`E0005` は未発行。
  仮パスワードは [`server/tsunagu_server/operator_tools.py`](server/tsunagu_server/operator_tools.py) の `DEMO_TEMP_PASSWORD`。
  初回ログインで新しいパスワードの設定を求められます。
- データは `server/var/tsunagu.db`（Git 管理外）。消せば次回の起動でデモ企業が作り直されます。

アプリ:

```bash
cd tsunagu/app && flutter run             # iOS シミュレーター・macOS など
```

接続先の既定は `http://localhost:8790`（Android エミュレーターは `http://10.0.2.2:8790`）。ログイン画面の「詳細設定」で変更できます。

テスト:

```bash
cd tsunagu/server && python3 -m unittest -v
```

## アカウントの流れ

1. **企業の作成（サービス運営者）**
   `python3 tsunagu/server/run.py create-company --code ACME --name "株式会社〇〇" --admin-code A0001 --admin-name "山田 太郎"`
   → 最初の管理者の「アカウント発行のお知らせ」PDF ができる。
2. **社員の登録（企業管理者）** 管理コンソールで 1 人ずつ、または CSV で一括登録。
3. **アカウント情報の発行** 社員を選んで「PDFで発行」または「メールで発行」。
   - 仮パスワードはこの時だけ作られ、サーバーにはハッシュしか残らない（再表示はできない。必要なら再発行）。
   - PDF は 1 人 1 ページ。企業コード・社員コード・メールアドレス・仮パスワード・有効期限・手順・取り扱い注意を印字。
   - 再発行すると、それまでのパスワードは無効になり、ログイン中の端末もログアウトされる。
4. **初回ログイン** 仮パスワードでログインすると、パスワード再設定だけができる限定セッション（30 分）になる。
   新しいパスワードを設定すると通常のセッションに切り替わる。
5. **パスキー（任意）** ログイン後、メニューの「パスキー」から登録。次回から指紋・顔認証でログインできる。

### パスワードの規則

- 8 文字以上・英字と数字を必ず含む・半角の記号も使える（空白・全角は不可）
- 社員コード・メールアドレスを含まない、よくある弱いパスワードでない、直近 5 回と同じでない、仮パスワードと同じでない
- 企業ごとに「最小文字数（8〜64）」「記号を必須にする」を設定できる

## 企業向けとしての配慮

- **テナント分離**: すべてのデータが企業に属し、問い合わせは必ず企業で絞り込む。別企業のデータは存在しないものとして扱う（テストあり）。
- **自己登録なし**: 社員が自分でアカウントを作る経路はない。退職・休職は管理者が「退職」「利用停止」にすると即時に全端末からログアウト。
- **ログインの防御**: 失敗時は「どれが違うか」を返さない／5 回失敗で 15 分ロック（企業設定で変更可）／IP ごとの回数制限／
  利用停止などの状態はパスワードが正しい場合だけ伝える。
- **秘密情報の扱い**: パスワードは PBKDF2-SHA256（60 万回）でハッシュ化。セッショントークンはハッシュで保存。
  アプリはトークンを OS の安全な保存領域にだけ置く。監査ログ・メール送信履歴（本番）に仮パスワードは残さない。
- **パスキー**: WebAuthn。本人確認（指紋・顔など）必須、署名カウンタの巻き戻しを検知。アプリはブラウザ経由で認証し、
  PKCE 付きの 1 回限りのコードで戻す（他のアプリに横取りされない）。
- **監査ログ**: ログイン成否、パスワード変更、アカウント発行、権限・状態の変更、削除、通報対応などを記録し、CSV で出力できる。
- **コンテンツの管理**: お知らせ（管理者のみ・「確認しました」と未確認者一覧）、通報 → 管理者が非表示、
  削除・編集しても監査のため本文と履歴は保持、利用ガイドラインへの同意（改定すると再同意）。
- **持ち出し対策**: アプリに外部共有ボタンを置かない。Android は自動バックアップ無効。

## 本番にする前に必要なこと

この試作は「動く形を一通りそろえる」段階です。本番運用の前に次が必要です。

- **HTTPS と独自ドメイン**: パスキーは HTTPS（または localhost）でしか動かない。`TSUNAGU_PUBLIC_URL` と `TSUNAGU_RP_ID` をそのドメインに。
- **メール送信**: `TSUNAGU_MAIL_MODE=smtp` と `TSUNAGU_SMTP_*` を設定（既定は送信せず管理コンソールに保存する開発モード）。
- **サーバー基盤**: いまは Python 標準ライブラリ＋SQLite。利用規模に応じて PostgreSQL などと、実績あるフレームワーク・
  WebAuthn ライブラリ（py_webauthn 等）への置き換え、バックアップ、監視を検討。API の形は変えずに差し替えられる構成にしてある。
- **プッシュ通知**: 今は 60 秒ごとの確認。APNs / FCM（Apple Developer Program・Firebase が必要）。
- **その他の候補**: 画像・ファイル添付（ウイルス検査つき）、ダイレクトメッセージ、SSO（SAML / OIDC）、MDM 配布、
  データ保持期間の設定、IP 制限、PDF のパスワード保護。

## 確認できていること・いないこと

- サーバー: 自動テスト 15 件（ログイン・初回再設定・ロック・発行・テナント分離・パスキー登録/ログイン/不正の拒否など）。
  パスキーの署名検証は OpenSSL で作った ES256 / RS256 署名でも確認。
- 管理コンソール: ブラウザで、初回ログイン → パスワード設定 → 社員追加 → メール発行 → PDF 発行 → 送信履歴・監査ログまで操作して確認。
  PDF は Chrome の PDF ビューアで日本語の表示を確認。
- アプリ（iOS シミュレーター）: 仮パスワードでログイン → 初回パスワード設定 → ガイドライン同意 → タイムライン・お知らせ表示 →
  投稿まで、サーバーにつないで確認。Android・macOS・Windows のビルドと、パスキーの実機での往復は未確認。
